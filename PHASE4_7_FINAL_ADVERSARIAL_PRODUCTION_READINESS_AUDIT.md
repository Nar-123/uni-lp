# PHASE 4.7 — FINAL ADVERSARIAL PRODUCTION READINESS AUDIT

## 1. Executive Summary

This is a zero-trust, full-lifecycle audit of the trading bot, re-derived from current source rather than from prior phase reports. It combines (a) my own direct, first-hand re-verification of the entire transaction-critical path — journal, broadcast, receipt wait, close fallback, recovery, accounting, TP/SL, instance lock, fatal-error handling, minOut/slippage enforcement — and (b) an independently-run, skeptical audit of the discovery → filtering → pool → range → sizing pipeline and a security/resource/test-integrity sweep, whose findings I personally re-verified against current source line-by-line before accepting any of them.

**Outcome: 6 real P1 findings were discovered and fixed this phase** (1 in the transaction-critical path, 5 in the MULTI strategy's candidate/pool/sizing pipeline). Each fix is minimal, matches an existing established pattern elsewhere in the same codebase, and ships with a focused regression test proving the specific defect is closed. 13 new tests were added; the full suite grew from 524 to 537, all green. Typecheck and build are clean. No prior-phase work was reverted, reset, or discarded.

**Decision: READY WITH CONDITIONS.** See §37 for the full reasoning and §50 for the exact conditions.

In scope: the complete MULTI/manual lifecycle from candidate discovery through close/reconciliation, on current source as of this session. ## 5–33. Lifecycle Stage Audits

Findings from every pipeline stage are consolidated into the findings table (§35) rather than repeated stage-by-stage here, to avoid duplicating the same content twice. Stage-specific narrative:

- **Candidate discovery / GMGN CLI (§5–8):** spawn safety, argument-injection defenses, timeout/SIGTERM→SIGKILL escalation, and failure classification were independently re-verified by the agent against current `src/gmgn/cli.ts` and found genuinely correct (no shell, array-form spawn, allowlist-validated args, sticky timeout classification). One real gap: a schema change in GMGN's trending response silently degrades to an empty candidate list without surfacing `sourceError` (F-06, P2).
- **Filtering / ranking (§9–10):** null/NaN handling fails closed correctly throughout; ranking is a deterministic total order. No minimum-volume filter exists despite volume being described as a filter criterion (F-07, P2).
- **Quote-asset validation (§11):** address-based (never symbol-based) comparison is correct and has real adversarial test coverage — except the env-var resolution path, fixed this phase (F-01).
- **Pool discovery / scoring (§12–13):** `scoreMultiPool`'s NaN/Infinity/negative hardening (Phase 4.6.7) was independently re-verified intact. Pool-fetch failure was silently indistinguishable from "no pool exists" — fixed this phase (F-02). Pool TVL/volume are trusted from DexScreener without on-chain cross-check (F-08, P2); MULTI's automated pool selection never calls `resolvePoolFromFactory` (F-09, P2).
- **Range calculation (§14):** re-verified as the single strongest area in the codebase — every adversarial tick/spacing/width input throws rather than producing a nonsensical range; the protocol-bounds and in-range guards are re-asserted at three independent layers.
- **Position sizing / exposure (§15):** two real, fixed P1s (F-03 exposure-cap arithmetic, F-04 fail-open missing-metadata default) plus a fixed P1 fabricated-price fallback (F-05).
- **Quote / price / minOut / slippage (§16–18, Part K's mandatory search):** exhaustive repo-wide search for `amount0Min=0`/`amount1Min=0`/`amountOutMinimum=0`/`minOut=0` patterns — see §17 below, all 5 occurrences verified BY DESIGN. `requirePositiveMinOut` in `safety.ts` is a real, enforced invariant (throws on `minOut <= 0`) wired into every local swap path. The GMGN-routed swap path (`src/gmgn/swap.ts`) does not locally construct or on-chain-enforce its own minOut — it validates the external quote's shape, matches `amount_in`, and requires `min_output_amount > 0` (`validateQuote`, swap.ts:100-124) before trusting GMGN's own pre-built calldata, which is standard practice for aggregator integrations (the aggregator's own contract enforces its own minOut). This is a documented trust boundary, not a bypass — see F-11.
- **Simulation / gas (§19–20):** every write path in `close.ts`/`v4.ts`/`mint.ts` calls `client.simulateContract` (or an equivalent dry-run `client.call` for the GMGN router path) before `writeContract`/`sendTransaction`; a simulation failure throws and no broadcast occurs — re-verified directly in `close.ts`'s multicall retry loop (lines 340-370) and `gmgn/swap.ts` (lines 210-220).
- **Transaction journal / submission / receipt / close fallback / recovery (§21–26):** fully re-verified in `clients.ts`, `txRecovery.ts`, `db/index.ts`. `journalledSend`'s pre-send refusal gate, journal-before-broadcast sequencing, fail-closed error classification (`classifyBroadcastError`), and the Phase 4.6.3 concurrent-recovery rewrite are all intact and match prior reports exactly — no discrepancy between source and prior documentation found here.
- **Accounting (§27):** the "one economic transaction → one economic accounting effect" invariant was **violated** for the TP/SL-triggered close path specifically — fixed this phase (F-00, the first finding, in §35).
- **Crash/restart, TP/SL, concurrency (§28–30):** re-verified via full re-read of `tpslWatcher.ts`; the Phase 4.6.4 shutdown/cancellation lifecycle (bounded wait, timer cancellation, forced-exit fallback) is intact and correctly implemented.
- **Failure injection matrix:** see §31.
- **Security, resource growth, test integrity (§32–33):** see §35 (F-10 through F-16) and §48.

## 37. Final Production Decision Reasoning

Per the decision framework: **no unresolved P0 or P1 remains** (6 were found this phase; all 6 were fixed with minimal, tested patches). No demonstrated path exists where duplicate economic execution is possible, an UNKNOWN transaction cannot eventually be recovered, minOut/slippage can be silently bypassed on a real withdrawal, or a simulation failure still results in a broadcast. Several P2/P3 findings remain **open and documented** (F-06 through F-16) — none of them directly affect transaction safety in the sense the framework uses ("duplicate tx, unsafe execution, accounting corruption, unrecoverable state"); they are reliability, observability, and coverage gaps in the candidate/pool selection layer, not the execution/accounting layer. This is exactly the profile the framework assigns to **READY WITH CONDITIONS**, not NOT READY (no unresolved P0/P1) and not unconditional READY (real P2s remain, and live network reachability was not verified this session).
